# Features

Items use the states `[ ]` waiting, `[~]` active, `[o]` complete, `[!]` held and `[-]` closed.
- [o] A1 — P1: The manifest `plugin.json` declares the identifier `agents`, the name, the description and the two sections `agents.running` and `agents.definitions` as view sections with their pages (A3 and A4). `test/manifest-shape.test.mjs` checks the declaration against the manifest rules of the core plugin specification.
- [o] A2 — P1: The agent accounts are a list in the project data of the plugin. Decision: accounts are the key `accounts` in `data`, with the schema of an array of objects `{id, cli, args, env}` and the default `[]`, not a core setting, because a settings declaration holds one scalar value (`docs/spec/plugins.md#settings-declarations`). `cli` is the program name of the agent CLI, `args` its arguments and `env` the names of the environment variables that the program receives; no variable value is stored. The form enters `args` and `env` as text with one entry per line. The commands `agents.account.define {id, cli, args, env}`, which adds an account or replaces the account with the same identifier, and `agents.account.remove {id}` run from the page `ui/accounts.html` with `ui/accounts-view.js`, which the section `agents.accounts` shows. The rules are in `ui/accounts.js`, and `test/accounts.test.mjs` checks them. Red: `test/accounts.test.mjs` failed with `Cannot find module` for `ui/accounts.js`, and the manifest tests failed with the section and the data key missing. Green: all 53 tests of `pnpm test` pass. The window check of the page is not run here.
- [~] A3 — P1: The running agents section `agents.running` lists the agent tabs of the window as the group, card and tab tree of `core.grid`: a tab of any plugin whose `params.program` is set, named by `params.role` or else `params.program`, with the activity of each tab from `core.activity`. No core status gives a view the program state of a tab: `core.activity` gives only the activity level of each tab, and the terminal statuses that hold the program state are refused to this view. Waits for: a core status that gives a view the program state of each tab, which core does not declare, and the window check of the section in the running app.
- [~] A4 — P1: The agent definitions section `agents.definitions` shows the groups of the project and lets a person create an empty group. The groups are project data under the key `groups`, declared in `data` with the schema `object` and the default `{}`; core stores the whole value of the key, which holds each group identifier with `{name, members}` and an empty `members` until A5. The command `agents.group.create {name}`, declared in `exposes`, adds the group with `runtime.data.change`; the page `ui/definitions.html` with `ui/definitions.js` lists the groups and enters the name through the binder. The group rules are in `ui/groups.js` (5 tests). Waits for: the window check of the page in the running app. Definitions in a group are A5.
- [o] A5 — P1, follows F1063 of the core checklist: A definition is a role that belongs to one group and carries the agent that runs it. The project data key `definitions` (`data`, schema `object`, default `{}`) holds each definition identifier with `{name, account, plugin, role, cwd}`. `role` is the core role identifier, which equals the definition identifier. `plugin` is the value of the setting `terminalPlugin` (declared in `settings`, default `terminal`) at the time of the definition, so no plugin name is a literal in code. `program` and `args` are not stored: a read resolves them from the account (`cli` and `args`). `agents.definition.define {group, id, name, account, cwd, text, ko, files}` checks the group and the membership, that the account is defined, that `name` has 1 to 40 characters and that `cwd` is an absolute path, then runs `core.role.define {id, text, ko, files}` and stores the definition and adds the identifier to the members of the group. `agents.definition.remove {group, id}` runs `core.role.remove {id}` and removes the definition and the member. `agents.account.remove` refuses an account that a definition uses. The members hold identifiers only: the page reads the text, the Korean text and the files of each member from the status `core.roles`, and a member that `core.roles` does not define is shown as not defined. A refusal of core stops the command with its text, and nothing is written. The rules are in `ui/definition-records.js` and `ui/roles.js`; `test/definition-records.test.mjs` and `test/roles.test.mjs` check them. Red: `test/definition-records.test.mjs` failed with `Cannot find module` for `ui/definition-records.js`; the manifest declarations were added with the manifest test, and their Red run was not recorded. Green: all 64 tests of `pnpm test` pass. The window check of the page is not run here.
- [~] A6 — P1, follows F1062 of the core checklist: The running agents use owned sessions of core: a definition's agent starts in a session that no tab holds, and a tab shows it on request. The running view wires both commands and watches `core.sessions`; the size of a new session is the view size and the device scale. Tests `test/sessions.test.mjs` (Red: the module was missing; Green: `node --test test/` passes 42 tests). This is a constraint of the section's lifetime, not a pending item. (4) No row of the running section lists a session that no tab shows; this unit adds the commands only, and the row waits for (2) to be verified in the window.
